# M6.6 — неподключённая KvFS не означает пустой диск

## Состояние и явная проверка

Boot, Programs и shell-команды df/dls/dcat/apps/install/uninstall больше
не выводят «диск не размечен, выполните format» из одного mounted=false.
Отсутствие подписи KvFS может означать другой формат или повреждение;
I/O fence также снимает mounted. Данные могут существовать. Форматирование
не предлагается как восстановление.

В Programs при неподключённой KvFS доступна «Проверить / подключить».
Это один явный вызов существующего kvfs_mount: чтение superblock/каталога
и полная проверка имён/extents/overlap, без записи, retry, USB/AHCI rescan
и без автоматического повторения неизвестной операции. Результаты
отсутствия ATA, read I/O, foreign signature и invalid metadata различаются.
При успехе недостающий /mnt/kv регистрируется без дубликатов.

vfs_namespace_changed — nonzero generation bump без I/O, очистки mount
таблицы или пересканирования устройств. Native kvfs_mount/kvfs_format
инвалидируют namespace при входе, даже при отказе; неизвестная публикация
metadata инвалидирует его вместе с mount fence. Это охватывает legacy
вызовы и installer, а не только новую GUI-кнопку. Старый открытый FM
name-dialog после такого изменения не выполняет действие по старому snapshot.
Per-pane namespace-at-load до открытия диалога остаётся следующим M6.7.

## Разрушительное форматирование

Первый клик «Стереть / разметить...» только открывает предупреждение:
номер/capacity boot ATA диска, потеря всех записей KvFS и явное «это НЕ
восстановление». Запись возможна только отдельной кнопкой «Стереть».
Enter не подтверждает; Esc/Cancel/закрытие окна/выход из GUI отменяют.
Пока вопрос открыт, другие controls Programs не выполняются.

Перед записью сверяются software drive index, capacity и namespace epoch
с сохранённым запросом. Это не проверка физической уникальности носителя
и не ATA hotplug qualification: одинаковый заменённый диск нельзя отличить
только этими полями. Отказ форматирования не обещает неизменность диска.
Сам format очищает записи/superblock KvFS, а не выполняет secure erase
содержимого; boot region до LBA2048 и data extents не перезаписываются.

Typed shell format остаётся явной destructive командой, не новой GUI-
подсказкой восстановления. Сообщение её ошибки не использует write-specific
kvfs_error как описание mount/format ошибок. Успех регистрирует /mnt/kv,
если тома ещё не было.

## Проверки и границы

- ASan/UBSan policy: exact software drive/capacity/nonzero generation,
  stale/wrap/missing/null refusal, без I/O.
- Реальный KvFS host backend: mount читает 9 секторов и пишет 0; read I/O
  и foreign signature не меняют image; mount/format/fence invalidation,
  before/after-publication fault модели, все прежние COW/rename tests PASS.
- VFS generation wrap→1 сохраняет mount table и не запускает scans.
- Полный host regression m66-host-all.log PASS. Отдельный GPT/owned-WAL
  regression с реальными FAT/NTFS/VFS/RAMFS drivers на private file images
  m66-fs-native-drivers.log PASS. Исправлена устаревшая host FS harness
  совместимость с M6.3 rename callback/header/IRQ host guard.
- BIOS/i386 и UEFI/x86-64 GRUB/direct ISO build: m66-release-final.log PASS.
- m66-state-native.log: production BIOS32+UEFI64 measured mouse PASS.
  Foreign signature и 6 shell отказов сохраняют image; первый клик format,
  Enter/Cancel/Esc/close не пишут; отдельный erase меняет только KvFS metadata,
  cold mount пустого каталога и новый VFS том PASS. Real metadata EIO →
  namespace fence → explicit read-only mount/check → проверка старого имени →
  отдельное новое действие → cold persistence. Diskless controls отсутствуют.
- m66-{rename,copy,workshop,cpu,sdk}-native.log: все suites обеих архитектур
  PASS. Первый combined process дошёл до SDK и отказал из-за отсутствующей
  после cleanup boxes32.kapp, не из-за kernel assertion. После явного
  SDK all/runtime build SDK PASS; начальный traceback сохранён отдельно.
- kvantos-m6-6-sdk-44dc61c9 exit0: SDK и тот же state/format сценарий
  на 640×480 обеих архитектур PASS (m66-state-small-native.log).
- m66-layout.log: direct/CD/floppy/installed BIOS layouts и 11 apps/arch PASS.
  SHA256 обоих kernel binaries после дополнительных SDK builds не менялся.
  CI recipe добавлен; hosted CI не запускался.

После очистки toolchain восстановлен. Fresh Python venv показал, что
Unicorn 2.1.0 требует pkg_resources; добавлен setuptools<81, включая CI
recipe. Начальный env failure сохранён отдельно; тесты не ослаблены.

Восстановлен Git baseline f710936 из проверенных M6.5 source hashes:
442 файла совпали с предыдущим proof, кроме намеренной записи о паузе в
очереди. Историческая цепочка commits не выдумывалась и не переписывалась.
M6.5 proof и source/WIP backup сохранены, protected3chmod не закоммичены.

Hosted CI, physical storage, TT recovery, FPU/float, FAT/NTFS rename и
cross-volume move не квалифицированы этим increment. Нет push/tag/release
или работы с host block devices.
