# M6.1 — bounded file-manager copy и незавершённые операции

Найден реальный дефект: fm_copy принимал любой got>=0 как успешное чтение и
записывал got bytes. Short/zero read большого файла мог молча заменить
назначение усечённой копией. Теперь **до vfs_write требуется got==size**.

- Сохраняется FM_COPY_LIMIT4MiB, один heap buffer, source никогда не удаляется.
  Zero-size source допустим. OOM/read error/short/oversized count → нет target write.
- Source/target paths проверяются до join: фиксированные bounded scans, basename
  не пустой/./../с slash/backslash, NUL обязан быть в пределах поля. Path255
  принят,256 отвергнут до allocation/I/O; truncated path не становится другим файлом.
- Одинаковые полные path strings — явный no-op без записи. Это не общий
  canonicalization/alias proof для произвольных искусственных VFS paths.
- VFS namespace epoch захватывается до I/O и проверяется после read: при смене
  mounts назначение не записывается. При epoch change во время write или неверном
  положительном byte count нет сообщения успеха: source оставлен, target нужно
  проверить. Нет blind retry/delete/rollback неизвестного результата.
- Это не atomic cross-volume move, не concurrent VFS locking и не новый WAL.
  Backend atomicity/physical generation fences по-прежнему обязательны.
  Политика overwrite по явной Copy action не менялась; rename/move ещё OPEN.
