# M6.19 — Initialized Size внутри allocated cluster

## Дефект

После M6.17 драйвер корректно zero-fill-ил хвост, если Initialized Size совпадал
с границей кластера. Но при чтении участка, который пересекает Initialized Size
внутри кластера, цикл ограничивал число итераций до initialized prefix, а размер
одной операции чтения всё ещё рассчитывал от полного requested length. В результате
он мог скопировать poison-байты из остатка первого allocated cluster до применения
zero-fill.

## RED → GREEN

Fixture теперь создаёт 1MiB nonresident file с двумя физически несмежными runs и
Initialized Size ровно 1234 байта (не кратно 4096-byte cluster). Все allocated
байты начиная с offset 1234, включая хвост первого кластера, заполняются `0xA5`.
`ntfsinfo` подтверждает Initialized Size; `ntfscluster` подтверждает полные два
runs; независимый `ntfscat` возвращает prefix + нули.

Контрольный RED: harness с kernel source до M6.19 сообщает byte-exact full read и
nonzero-offset read как FAIL (10 PASS, 2 FAIL). Production fix считает каждый
cluster-read только по `data_want - done`; после него полный image adapter suite
PASS, в том числе чтение через 1234-byte границу и точный poisoned suffix.

## Результат и границы

Private regular-file NTFS fixture, read-only adapter, zero block writes и unchanged
whole-image SHA. Никаких host mounts или физических устройств. Проверка относится
только к точке Initialized Size внутри одного кластера этого clean 1MiB two-run
fixture; произвольная NTFS interoperability и иные fragmentation patterns не
заявляются. Полные regression logs и validation JSON включены в M6.19 proof.
