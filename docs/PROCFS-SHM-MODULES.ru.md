# Идеи ToaruOS для KvantOS: реализация и границы

## Источник и лицензия

Изучена [ToaruOS](https://github.com/klange/toaruos) на фиксированной ревизии
`60b54503807a38ae1f0692d44cf8b569301febbc`:

- [kernel/vfs/procfs.c](https://github.com/klange/toaruos/blob/60b54503807a38ae1f0692d44cf8b569301febbc/kernel/vfs/procfs.c):
  генерация текстового снимка **при открытии**, чтение с offset, освобождение при close;
- [apps/yutani.c](https://github.com/klange/toaruos/blob/60b54503807a38ae1f0692d44cf8b569301febbc/apps/yutani.c):
  сервер создаёт общие пиксельные буферы через shm_open/mmap, согласует resize,
  освобождает старые отображения; затем композитит изображение;
- [kernel/sys/mman.c](https://github.com/klange/toaruos/blob/60b54503807a38ae1f0692d44cf8b569301febbc/kernel/sys/mman.c),
  [kernel/misc/elf64.c](https://github.com/klange/toaruos/blob/60b54503807a38ae1f0692d44cf8b569301febbc/kernel/misc/elf64.c)
  и [module.h](https://github.com/klange/toaruos/blob/60b54503807a38ae1f0692d44cf8b569301febbc/base/usr/include/kernel/module.h):
  отображения памяти, ET_REL, релокации, таблица загруженных модулей и init/fini.

Лицензия upstream — **University of Illinois/NCSA**, не MIT. Здесь самостоятельно
написана реализация под существующие интерфейсы KvantOS; исходный код ToaruOS
не включён в дерево или сборку. Это использование архитектурных идей, не перенос
совместимого VFS/Yutani/ELF-loader. При дальнейшем включении upstream-кода нужно
сохранить его copyright, все условия NCSA и disclaimers также в материалах
бинарного дистрибутива; MIT KvantOS не заменяет эту обязанность.

## Реализовано: read-only `/proc`

Монтируется после sched_init, в том числе в safe mode. Поддерживаются оба пути
`/proc/...` и `/mnt/proc/...`. Это системный том вне восьми слотов накопителей:
все восемь физических/обычных томов остаются доступны. Он переживает vfs_init
при `rescan` и GUI-пересканировании; generation VFS при этом меняется как прежде.
Повторная регистрация идемпотентна. Обычный том не может занять имя `proc`.

| Файл | Поля и смысл |
|---|---|
| cpuinfo | Архитектура сборки, CPUID vendor и model |
| meminfo | MemTotal, MemUsed, MemFree, **kB = 1024 байта**, по PMM-кадрам |
| uptime | Полные 64-битные PIT ticks / фактическая TimerHz, секунды с сотыми |
| stat | Число живых kernel tasks, TimerHz, полные Ticks |
| version | Имя ОС, версия, архитектура |
| `<id>/status` | Kernel-task ID, имя, ready/sleeping, число переключений на задачу |

Это **задачи ядра, не POSIX-процессы**. Текущая задача имеет состояние ready,
а не отдельное running. DEAD-задачи не публикуются. Здесь нет выдуманных
процентов загрузки CPU, RSS/памяти задачи, свободного heap, адресов стеков/ESP
или указателей ядра. MemFree — свободные кадры PMM, не свободные байты kmalloc;
зарезервированная куча учитывается как занятая физическая память.

Идентификатор — каноническое десятичное u32, включая 0; `00`, `+1`, отрицательные,
переполнения, dot-компоненты, лишние компоненты и `self` не поддерживаются.
Имена/CPU-строки выводятся ASCII, управляющие и не-ASCII байты заменяются `?`.
Запись, удаление, переименование, создание каталогов запрещены через VFS.
Это не дисковый том: объём/свободное место равны 0 и никакого block I/O нет.

### Согласованность: важное отличие от ToaruOS

Нынешняя VFS KvantOS имеет только `read(path, offset, max)` / `size(path)`,
**без open/close и без дескриптора снимка**. Поэтому:

- каждый вызов read генерирует свой снимок в ограниченном буфере на стеке;
- числовые/изменяемые поля имеют фиксированную **байтовую** ширину с пробелами;
  size и границы строк/полей не сдвигаются при изменении значений;
- offset/EOF/огромный offset и ограничение max обрабатываются без сложения,
  которое могло бы переполниться;
- маленькие последовательные read могут увидеть цифры из **разных моментов**.
  Фиксированные смещения предотвращают смещение текста, но не смешивание цифр;
  для одного согласованного содержимого читайте весь файл одним read;
- для меняющихся task-каталогов нет снимка всей выдачи readdir. При появлении/
  исчезновении задач возможны пропуски/повторы; повторите перечисление при нужде;
- задача может исчезнуть между stat/size/read: отсутствие/ошибка чтения — штатный
  исход. Здесь нет обещания POSIX snapshot-on-open или стабильного PID lifetime.

task_snapshot_id/nth копируют только скалярные поля и имя под коротким IRQ guard
на текущем однопроцессорном ядре. После восстановления IRQ указатель task_t
не удерживается: reaper вправе его освободить. Обход ограничен **посещёнными**
узлами (256), а не числом живых; кольцо из DEAD не зависает. Некорректная/
слишком длинная структура возвращает ошибку; это не защита от произвольной порчи
памяти. task_count также использует ограниченный обход. Публикация «нет задачи»
и «пустое перечисление» не создаёт новый объект и ничего не выделяет в heap.
64-битные ticks считываются под IRQ guard, деление не требует libgcc на BIOS32.

### Использование

```text
mount
vls /proc
cat /proc/cpuinfo
cat /proc/meminfo
cat /proc/uptime
cat /proc/stat
cat /proc/0/status
vcat /mnt/proc/version
rescan
cat /proc/meminfo
```

`cat` с абсолютным путём теперь обращается к VFS; старый `cat readme.txt`
продолжает читать плоскую RAMFS. Для относительных путей VFS после `vcd`
используйте `vcat`. File Manager видит системный том через обычное перечисление
томов. Реализация доступна **kernel VFS**, не добавляет новые syscall.

**Ещё не переведены** `ps`, `mem` и графический Monitor: они используют старые
внутриядерные API. Не изменён и замороженный ABI native `.kapp`: его файловые
функции по-прежнему обращаются к KvFS. KS_OPEN/READ user-service пока работают
с частными RAM-файлами, а не произвольной VFS. Таким образом, произвольная
ring3-программа ещё не может открыть `/proc`; следующий отдельный шаг —
read-only VFS handles с ownership и снимком на open в версионированном service API,
затем перевод клиентов. Не нужно вводить по syscall на каждый вид метрик.

## Реализовано: экспериментальные shared surfaces GUI (protocol2)

`kernel/user_space.c` теперь различает частные и общие страницы. `ku_shared`
владеет кадрами: owner-reference плюс ссылка каждого PTE. Снятие owner запрещает
новые отображения, но не обнуляет память, пока остались mappings. Последняя ссылка
обнуляет и освобождает кадры ровно один раз. Сам объект — стабильная kernel-owned
структура: её память нельзя уничтожать, пока `live != 0`. API требует прежней
сериализации caller-ом; pinned space нельзя менять или уничтожать.

`kernel/user_surface.c` выделяет два ARGB8888-буфера, отображает их в свободную
непрерывную область arena приложения и передаёт только offsets/geometry/generation.
Начальный front read-only, back writable. PTE-защита меняет **все aliases данного
объекта в этом space**, не только первый адрес. Другой space не получает объект
через service API. KU_X для shared mappings запрещён API; аппаратный NX включается
на поддерживающем его x64. BIOS32 без PAE/NX не обеспечивает hardware non-execute,
но аппаратная read-only защита front работает и на i386.

### Протокол и публикация

- KAPP format2 ABI4: поле protocol в заголовке может быть **1 или 2**.
  Прежние format1 ABI2/3 и format2 protocol1 не переключаются автоматически.
- protocol2 — явное opt-in. При загрузке создаётся пара **420×300**, примерно
  992 KiB физических кадров (248 страниц), плюс private pages/page tables.
  Нехватка кадров/места в arena отклоняет загрузку с rollback; работающий чужой
  процесс не получает эти страницы. Это пока один app, не multi-client compositor.
- `KS_QUERY` возвращает `KS_CAP_SURFACE=128` только владельцу настроенного surface.
- `KS_SURFACE_INFO=16`: `a=out_offset, b=32, c=d=0`. Возвращает 32-байтный
  `{version=2,bytes=32,generation,width,height,stride,offset[2]}`.
- `KS_SURFACE_PRESENT=17`: `a=back_index, b=sequence, c=d=0`, token текущего
  доставленного DRAW. Начальный front=0/back=1, sequence=1. Неверные generation,
  phase, token, повтор, front index и sequence отвергаются. Публикация пока
  **отложена**: очередь не меняет PTE и не открывает compositor-у back.
- Только `KS_COMPLETE` возвращает управление в kernel CR3 через ku_mode_leave.
  Runtime с выключенными IRQ временно снимает pin, делает новый front read-only,
  прежний front writable и восстанавливает pin. Следующий resume перезагружает
  user CR3, очищая TLB. На обычном quantum-yield публикации **нет**.
- Клиент может продолжать заполнять back до COMPLETE; после COMPLETE запись
  в опубликованный буфер вызывает user page fault. Это не кооперативный fence,
  который недобросовестный клиент может просто проигнорировать.

`kapp_draw` читает **те же физические кадры**, преобразует straight ARGB к формату
framebuffer и выполняет CPU alpha blending с clipping по client area. Сообщения
не содержат пиксельный массив, промежуточного app→compositor memcpy нет. Доступ
к front в этом однопоточном GUI синхронный: нельзя pump/unload между началом
и концом blit. При CLOSE/fault runtime снимает mappings, owner и private space;
последняя ссылка освобождает страницы. Уничтожение private space первым также
не обнуляет ещё принадлежащие surface кадры.

### Демо и текущие ограничения

```sh
make -C sdk/isolated all
make -C tests/mcc user-space user-service user-image user-surface
```

`pixels32.kapp` / `pixels64.kapp` — CPL3-демо с анимированными полупрозрачными
пикселями. Открывается обычным Program Manager из KvFS. `Q` завершает приложение,
`F` намеренно пишет в front: ожидается page fault только приложения с освобождением
его страниц. Бинарники генерируются в ignored build/, не включаются в Git.

**Пока нет** resize-handshake, динамической геометрии surface, dirty rects,
multi-client server, GPU acceleration и измеренного прироста FPS. При изменении
окна фиксированная surface лишь обрезается по client area; при увеличении окна
она не растягивается и не дополняется. Полная альфа-композиция и вывод в framebuffer
всё ещё требуют CPU/памяти. Работающий legacy drawing API не переписан на этот
механизм. Следующие этапы — безопасный resize с сохранением старых кадров до
release, bounded dirty regions и независимые бенчмарки, а не обещание «нулевых копий»
во всех частях графического тракта.

## Не реализовано: динамические драйверы ядра

ToaruOS ELF64 loader нельзя без проверки вставить в dual BIOS32/UEFI64 ядро.
Нужны отдельные ET_REL ELF32/i386 и ELF64/x86-64 пути, а не `.kapp` loader.
План из независимых проверяемых этапов:

1. Manifest с версией **kernel-module ABI**, архитектурой, зависимостями и PCI
   match; явная ограниченная таблица exports. Отказ при неизвестных импортных
   символах/версиях. Нельзя экспортировать произвольные внутренние адреса.
2. Bounded ELF reader из read-only VFS-файла: magic/class/machine/endianness,
   переполнения/диапазоны всех секций и таблиц, корректные string tables,
   SHT_NOBITS, alignment; allowlist релокаций для каждой архитектуры, проверка
   итоговых адресов и signed displacement. Неподдерживаемый тип — ошибка,
   не «пропустить и выполнить». Фаззинг на host до первого запуска модуля.
3. Отдельное размещение text/rodata/data, подходящие page permissions там,
   где архитектура/текущая paging это поддерживает; полный rollback выделений
   до init. Регистрация объекта только после успешной загрузки и релокации.
4. Централизованный PCI claim и явный bind: встроенный и внешний драйвер
   не должны одновременно владеть контроллером. Сначала тестовый модуль без
   DMA, затем отдельно квалифицированный кандидат (например, audio/EHCI).
5. Lifecycle init → live → quiescing → fini. Учёт IRQ handlers, таймеров,
   deferred callbacks, открытых устройств, зависимости от другого модуля,
   DMA rings. Unload разрешён только после остановки bus mastering/передач,
   отключения и синхронизации IRQ и обнуления всех ссылок. Если эти гарантии
   драйвер не предоставляет — он **невыгружаемый**, а не «попробуем освободить».
6. Bootstrap: драйвер диска/FS, с которого читается модуль, должен уже работать.
   Сначала оставить загрузочный ATA/AHCI и файловые драйверы встроенными;
   перенос bootstrap-драйверов возможен после отдельного initrd/boot archive.

Отрицательный код **init**, до передачи владения устройству, позволяет управляемый
rollback. Исключение внутри ring0-драйвера — совсем другая ситуация: возможны
испорченные данные ядра, захваченные locks и активный DMA. «Ядро просто выгрузит
упавший драйвер и продолжит» здесь **не обеспечивается**. Для такой границы отказа
нужны изолированные user-mode драйверы и контролируемые I/O/MMIO/IRQ; для
DMA ещё IOMMU либо безопасный mediated-kernel путь. Простого модуля недостаточно.

## Проверки

- `make -C tests/mcc procfs`: реальные procfs.c, vfs.c, scheduler snapshot-copy
  и cat/vcat с фиктивными устройствами, ASan/UBSan, настоящий formatter ядра.
  Проверяются все 8 дисковых слотов + system mount, rescan/reset, RO-мутации,
  canonical PID/переполнения, EOF/частичные чтения, фиксированные размеры,
  UINT64_MAX ticks и эталонные деления, исчезновение задач, DEAD/null/overlong
  кольца и отсутствие использования privileged IRQ инструкций на host.
- `make -C tests/mcc user-surface`: общие frames/aliases/owner revocation,
  OOM cuts, 100 front/back flips, page-walk RW/NX, deferred COMPLETE и teardown
  на моделях i386/x64 с ASan/UBSan.
- `python3 tests/boot/user-surface-smoke.py`: отдельный QEMU/CPL3 тест реального
  GUI, публикации, front-write fault, освобождения страниц и неизменности диска;
  включён в compiler-isolation CI, требует собранных ISO и SDK.
- `make -C tests/mcc vfs filemgr storage ramfs input` — соседние host-регрессии.
- Freestanding object compilation procfs/sched/VFS/main/shell — BIOS32 и UEFI64.
- `python3 tests/boot/procfs-smoke.py` — **отдельный реальный boot-тест** с QEMU,
  OVMF и собранными ядрами/ISO; включён в build CI. Host-тест не заменяет его.

Этот документ не утверждает, что boot/CI уже прошли в конкретном окружении,
что новый GUI путь уже прошёл VM/hardware-проверку, что kernel modules реализованы,
или что изменения включены в
замороженный тег релиза v3.4.0.
