# M6.13 — ограниченная NTFS image qualification

## Что выявил реальный образ

M6.12 проверял перевод logical LBA/count в 512-byte block API на synthetic
adapter fixture, но не реальный NTFS volume. Для M6.13 созданы приватные regular
files с помощью `ntfs-3g 1:2022.10.3-5+deb13u3` (`mkntfs`, `ntfscp`, `ntfscat`):
по 128 MiB, NTFS logical sector 512, 1024, 2048 и 4096 байт, простая
корневая запись `proof.txt`. `ntfscat` независимо подтвердил ожидаемые байты.

Первый фактический 4Kn образ (`mkntfs --sector-size 4096`) показал несовпадение:
MFT record имел USA count=9 и восемь fixup trailers с шагом 512 байт, тогда как
наш parser ошибочно использовал BPB bytes-per-sector=4096 и ожидал count=2.
Исправлен `apply_fixup`: NTFS Multi-Sector Transfer Update Sequence Array
проверяется по 512-byte stride, с точным count, проверкой маркеров, границ массива
внутри первого 512-byte block и всей записи. Это соответствует описанию Microsoft
для NTFS 4K sectors: [NTFS And 4K Disks](https://learn.microsoft.com/en-us/archive/blogs/ntdebugging/ntfs-and-4k-disks).
Добавлен 4KiB USA host regression: позитивный record, неверный count и проверка
восстановленных trailers.

## Qualification harness

`tests/fs/test_ntfs_image.py` и target `make -C tests/fs ntfs-image` создают
свежий `TemporaryDirectory` строго под `tests/fs/build/`, только regular files.
Для каждой геометрии тест:

1. Форматирует private image и проверяет BPB logical-sector size/volume extent.
2. Добавляет `proof.txt` только в этот образ утилитой `ntfscp`.
3. Проверяет эталон независимой `ntfscat`.
4. Запускает production NTFS/VFS/block drivers через host harness, открывающий
   образ read-only: autoscan, read-only mount, root listing, размер и byte-exact
   read файла.
5. Проверяет отказ VFS write/remove/mkdir; callback write count должен быть 0,
   и SHA-256 всего образа до/после driver test обязан совпадать.
6. Удаляет созданную временную директорию.

Для повторения нужны `mkntfs`, `ntfscp`, `ntfscat` из ntfs-3g; при нестандартных
путях можно задать `MKNTFS`, `NTFSCP`, `NTFSCAT`, а для динамической библиотеки —
`NTFS_LIB_DIR`. Ни script, ни harness не выполняют host mount, loop setup,
`/dev/*` access, physical writes или NTFS repair.

## Результаты и границы

- Actual ntfs-3g NTFS logical-sector images at 512/1024/2048/4096 bytes:
  root entry, size/read, RO refusal, zero block writes, whole-image SHA unchanged
  — PASS на каждой geometry; 4Kn проходит после 512-byte USA fixup correction.
- Полный MCC compiler/sanitizer/storage/VFS suite, 50k NTFS mutations,
  GPT22/owned-WAL/FAT-perf, GCC12 release/layout — PASS после исправления.
- BIOS32/UEFI64 native shell-path/vcp/listing/namespace/KvFS-state/CPL3/Workshop
  regression process `ntfs-bios-uefi-regression-b2f47b29` завершился exit 0;
  все сценарии PASS на обеих архитектурах.

Это ограниченная квалификация чистого ntfs-3g 3.1 test volume с простым небольшим
корневым файлом, проверенная host block adapter-ом. Это **не** подтверждение для
произвольных Windows volumes, грязных/шифрованных/сжатых/разреженных томов,
фрагментированных каталогов/файлов, долгой эксплуатации или физического SATA/USB
4Kn hardware. M6.14 отдельно квалифицировал MBR-offset path
(`docs/M6.14-NTFS-PARTITION-OFFSETS.ru.md`), а M6.15 добавил large nonresident
Unicode root file (`docs/M6.15-NTFS-NONRESIDENT-UNICODE.ru.md`); GPT offset and
nested Unicode directories остаются OPEN. NTFS остаётся только для чтения. Не
проводились host mount и физические I/O.
