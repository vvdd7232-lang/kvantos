# M6.16 — границы частичного NTFS-чтения

## Scope

Укрепить фактическую проверку VFS `read(path, offset, buffer, max)` на реальных
ntfs-3g regular-file образах: ненулевое смещение, чтение через границу сектора и
кластера, короткое чтение у EOF и поведение точно за EOF. NTFS по-прежнему только
для чтения; production NTFS-код не менялся.

## Fixture assertions

Для каждого файла в имеющейся M6.15 fixture harness проверяет:

- полный byte-exact read;
- ненулевое смещение 509 на 1MiB nonresident payload: чтение 4096 байт пересекает
  границы 512-byte sector и 4096-byte cluster; для короткого resident файла
  проверяется ненулевой offset к хвосту;
- запрос 4096 байт за последние 17 байт возвращает ровно оставшиеся 17 байт и
  точные данные;
- чтение с `offset == size` и `offset == size + 1` возвращает 0;
- остаются прежние listing, read-only, zero-write, no-OOB и неизменный image SHA.

Проверки идут на raw 512/1024/2048/4096 logical-sector образах и MBR LBA-2048
wrapper при 512/4096. Они используют те же независимые ntfscat/ntfsinfo
предусловия M6.15; nonresident `$DATA` по-прежнему явно подтверждается до
production adapter test.

## Результат

`make -C tests/fs CC=gcc-12 ntfs-image` — PASS 2026-10-17. Каждый actual-image
harness проход (включая оба файла, все raw геометрии и обе MBR геометрии) сообщает
12 PASS / 0 FAIL; malformed MBR extent — 3 PASS / 0 FAIL. В полном логе:
`build/autonomous/m616-ntfs-boundary.log`. Образы временные, private regular files;
никакого host mount, `/dev` или физического устройства.

## Ограничения

Это квалификация семантики offset/length/EOF для рассматриваемых простых
ntfs-3g файлов и созданных runlist-ов; это не доказывает arbitrary NTFS, fragmented
multi-run stream, nested Unicode directory, GPT-offset NTFS, Windows/dirty,
sparse/compressed или физическую 4Kn совместимость. Для M6.16 production
`kernel/ntfs.c` не менялся. Исторические M6.13 native BIOS32/UEFI64 доказательства
относятся к неизменному production NTFS source; M6.16 добавил host-test assertions.
