# M6.15 — nonresident NTFS file and Unicode root name

## Fixture and independent format checks

`tests/fs/test_ntfs_image.py` now creates two files inside each private ntfs-3g
regular-file image:

- small resident `/proof.txt`;
- `/Длинный файл.bin`, exactly 1 MiB, deterministic nontrivial payload.

`ntfscat` reads both and is byte-compared with the input fixtures. `ntfsinfo -F`
confirms the large file's `$DATA` attribute is **non-resident**; the test refuses
success if this precondition is not actually present. This is not inferred merely
from file size.

The production host block/VFS adapter then checks each file's existence/size,
UTF-8 name in root listing, bounded byte-exact read, denied write/remove/mkdir,
zero block writes, no out-of-range ATA callback and unchanged full-image SHA.
The 512/1024/2048/4096 logical-sector raw-volume matrix remains. The valid MBR
LBA-2048 and malformed one-sector-overrun variants for 512/4096 now read both
resident and nonresident files as well.

## Результаты

`make -C tests/fs CC=gcc-12 ntfs-image` PASS for all four logical sector sizes;
independent `ntfsinfo` explicitly verifies `$DATA Resident: No`. Actual MBR-offset
512/4096 fixtures also pass. `make -C tests/fs CC=gcc-12 gpt fat-owned fat-perf`
also passes (GPT22, WAL 1696 interruption cases, FAT perf). The test stores nothing
outside its generated `tests/fs/build/ntfs-image-*` temporary directory and removes
it on exit.

The fixture requires `mkntfs`, `ntfscp`, `ntfscat`, and `ntfsinfo` from ntfs-3g.
Nonstandard tool paths can be provided as `MKNTFS`, `NTFSCP`, `NTFSCAT`, `NTFSINFO`
with optional `NTFS_LIB_DIR`.

## Границы

Image creator/reader is ntfs-3g 2022.10.3. This is a clean, freshly formatted
fixture with one freshly allocated large file (not an intentionally fragmented
runlist) and one Unicode root-level file. No nested Unicode directory, multiple extents, sparse or
compressed stream, Windows-generated/dirty volume, GPT offset, physical 4Kn
hardware, or NTFS writes/repair is qualified. NTFS remains read-only. The external
fixture tools write only the disposable regular-file images before the OS driver
opens each image read-only; the production adapter itself produces zero writes.
