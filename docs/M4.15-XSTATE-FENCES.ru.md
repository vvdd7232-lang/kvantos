# M4.15 — xstate denial, включая inherited OSXSAVE

FPU/SIMD/context/float **не включены**. Укреплён действующий deny profile:
CR0.TS|MP=1, CR4.OSXSAVE=0 вместе с прежними PCE/FSGSBASE clear. Prior CR0/CR4
полностью восстанавливаются после каждого exit/yield/wait/fault. Обычные
ABI4 integer apps/старые ABI2/3/caps127 не требуют изменений.

## Найденный случай

Native test на QEMU10.0.13 (Debian10.0.13+ds-0+deb13u1), UEFI64/cpu max,
искусственно включил OSXSAVE до входа CPL3. TS-only policy позволила XSAVE
записать CPU state в private RW page и XRSTOR исполниться, оба дошли до
exit99 вместо ожидаемого fault. Проверка private output выявила запись.
Это наблюдаемый emulator path; физический CPU не проверялся, причина расхождения
со справочником #NM не объявляется установленной.

Исправление — не ослабить assertion или разрешить state access, а явно
очистить CR4.OSXSAVE на user entry. Теперь обе инструкции получают #UD6 даже
при inherited-enabled prior CR4, а исходный OSXSAVE возвращается ядру.
В пользовательской policy не нужен XSAVE, пока context backend отсутствует.

## Native probes

Помимо FLD1 теперь FWAIT/FNINIT/FNSTENV/FNSAVE, MMX PXOR, SSE XORPS,
STMXCSR/LDMXCSR, FXSAVE/FXRSTOR, XSAVE/XRSTOR; отдельно inherited-enabled
XSAVE/XRSTOR на CPUID.XSAVE CPU. Ожидаемый vector вычисляется по CPUID/host
CR0.EM/CR4.OSFXSR, а не принимается любой fault.

State operands находятся на mapped RW page, выровнены на64B. Поэтому guard
или alignment #PF/#GP не могут подменить требуемый #NM7/#UD6. После каждой
попытки первые1024B output проверяются на нули: не допускается даже частичный
state dump. report сверяет PMM, CR3/TSS, prior CR0/CR4/MSRs и process teardown.

  XSAVE family #UD6, в том числе inherited-enabled OSXSAVE.
