# M6.18 — отказ от NTFS volume-size truncation

NTFS BPB `total_sectors` — 64-битное поле, а текущий block/VFS path KvantOS
использует 32-битные номера 512-byte blocks и 32-битный размер тома. До M6.18
`parse_boot` читал только low DWORD. Поэтому образ с ненулевым high DWORD мог
ошибочно выглядеть как маленький volume по low DWORD — alias вместо отказа.

## Fix и воспроизводимый отрицательный fixture

`parse_boot` теперь считывает оба DWORD и отказывает, если high DWORD ненулевой.
Это fail-closed поведение: поддерживаемые образы не усечены; крупные объёмы,
которые API не может адресовать, не монтируются частично.

Test копирует только private 128MiB ntfs-3g regular file, задаёт `1` в BPB
`total_sectors` high DWORD (`offset 0x2C`) и запускает production host adapter.
Ожидается 0 смонтированных volumes, 0 out-of-bounds reads, 0 writes и неизменный
image hash. Никакого mount loop, `/dev` или физического устройства.

## Результат

`make -C tests/fs CC=gcc-12 ntfs-image` PASS для прежнего набора raw
512/1024/2048/4096, MBR offset 512/4096, partial/EOF, двух-run initialized-tail
fixture и нового high-DWORD отказа. MCC VFS/parser ASan/UBSan, GPT22,
owned-WAL1696/FAT-perf и clean GCC12 BIOS32/UEFI64/EFI build regression PASS.
Полный лог и validation JSON включены в proof archive.

## Граница

Этот тест подтверждает только отказ от high-DWORD truncation. Он не заявляет
поддержку NTFS volume-ов за пределом 32-bit block API, GPT-offset, arbitrary
Windows/dirty metadata, дополнительных runlist shapes или физического 4Kn.
NTFS остаётся read-only.
