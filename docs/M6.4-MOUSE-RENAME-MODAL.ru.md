# M6.4 — мышиный диалог имени

## Интерфейс

Файловый менеджер получил кнопку «Переимен.» и отдельный диалог с
«Применить»/«Отмена». Исходный путь показан отдельно; существующее имя
выделено целиком и заменяется первым вводом. Ctrl+A выделяет, Ctrl+U
очищает, Backspace удаляет целую UTF-8 последовательность. Русская
раскладка проходит через существующий keymap_utf8; навигационные KEY_UP
и другие special keys не превращаются в Unicode-текст.

Диалог нового каталога использует тот же mouse-first UI. Пока ввод открыт,
клики по панелям/Volume/toolbar не меняют действие или его назначение.
Закрытие окна и выход из GUI отменяют незавершённый ввод без записи.
Клавиатурные альтернативы Enter/Esc/F7 оставлены, но для открытия и
подтверждения диалога достаточно мыши; одиночных клавиш запуска нет.

## Ограничения и безопасность

Снимок содержит исходный source path, каталог, pane, listing epoch и VFS
namespace generation **на момент открытия**. Изменение любого из них
до Apply отменяет действие до вызова backend. Это не per-pane фиксация
namespace на момент первоначального чтения списка; такой отдельный gate
остаётся в очереди, включая generation change посреди readdir.

Имя и итоговый путь проверяются до операции без truncation. Только один
basename; нельзя `.`, `..`, slash/backslash и ASCII control/DEL. Превышение
backend-предела 23/39 байт не обрезает имя: backend отказывает, диалог
остаётся открытым для исправления или отмены. При конфликте существующий
файл не заменяется. После успеха оба списка обновлены; активная панель
выбирает новое имя. Same-name backend no-op не пишет на диск.

При неопределённой публикации metadata или смене namespace во время
операции диалог закрывается с **Outcome uncertain**, без retry/rollback
и без обещания старого имени. Обновление списка не является remount или
recovery fenced KvFS. Нужны отдельный validated remount/проверка; native
тест использует cold boot, а не предполагаемое восстановление по Refresh.

`vfs_can_rename` честно проверяет writable + optional callback. FAT/NTFS
переименование и межтомовый move не появились. Native rename RAMFS/KvFS
по-прежнему следует M6.3; GUI не реализует copy/delete fallback.

Смежный namespace fix: resolve отвергает volume component длиннее поля,
а не маршрутизирует его по первым 15 байтам на другой том. Host regression
создаёт том с 15-byte именем и проверяет отказ для совпадающего длинного
префикса, а также capability/RO/unsupported поведение.

## Проверки

- `m64-host-all.log`: полный compiler/runtime/editor/storage/controller/FS
  host regression PASS. `m64-host-targeted-final.log`: реальные filemgr+VFS
  под ASan/UBSan, EN/RU. Snapshot changes, cancel, conflict/RO, bounded names
  и paths, Unicode/backspace/selection, unknown publication до/после записи,
  epoch во время callback, mkdir и отсутствие copy/delete.
- `m64-release-initial.log`: BIOS/i386 + UEFI/x86-64 GRUB/direct ISO build PASS.
- `m64-rename-native.log`: production BIOS32+UEFI64 PASS. Только measured
  mouse targets 719/720/721; modal barrier, cancel, conflict, same-name disk
  SHA, отказ имени 40 байт, русский ввод «файл.txt» и UTF-8 Backspace,
  persist/cold mount, обновлённые панели, genuine double-click, window-close
  cancel, RAM mouse rename, mkdir unsupported/cancel. Real blkdebug metadata
  EIO → честная неопределённость + mount fence → validated cold mount.
- `m64-copy-native.log`: существующая RAM→KvFS copy/samepath/identity
  regression обеих архитектур PASS.
- `kvantos-m6-4-native-regression-d7d63633` exit0: backend, Workshop, CPU
  и SDK обеих архитектур PASS, логи `m64-{backend,workshop,cpu,sdk}-native.log`.
- `kvantos-640-480-75e70547` exit0: тот же mouse rename/cancel/conflict/RU/
  EIO сценарий на 640×480 обеих архитектур PASS (`FM_SMALL=1`, отдельные
  `build/filemgr-rename-small/*/result.json`, `m64-rename-small-native.log`).
- `m64-release-final.log` PASS; SHA256 обоих kernel binaries до/после
  повторной упаковки совпадают, результаты native относятся к тем же ядрам.
  CI recipe дополнен default native mouse test; hosted CI не выполнялся.

Stale namespace/listing/path и after-publication fault injection — host-only.
Нет physical/hosted-CI/publication qualification и нет разрешения FPU/float.
